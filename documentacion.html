01 / Descripción del proyecto

Descripción y objetivo del proyecto

NeoConexión es un servicio backend independiente. Una plataforma externa envía perfiles y ofertas, mantiene sus identificadores y consulta recomendaciones. El sistema no publica vacantes ni administra postulaciones: resuelve la compatibilidad entre ambas partes.

ENTRADA

Candidatos y vacantes

Habilidades, experiencia, ubicación y modalidad de trabajo, recibidas como JSON a través de HTTP.

PROCESO

Procesamiento mediante grafos y reglas

Neo4j encuentra conexiones por habilidades. Python aplica la fórmula de compatibilidad a cada pareja seleccionada.

SALIDA

Recomendaciones explicables

Puntuación de 0 a 100, desglose por componente, habilidades presentes y faltantes, y razones en español.

Interpretable desde el principio. El resultado es una puntuación de compatibilidad definida por reglas. No es una probabilidad de contratación, ni una predicción de desempeño, ni una decisión automática de selección.
02 / Arquitectura

Arquitectura del sistema

Un único servicio organizado como monolito modular. Las capas separan el contrato HTTP, los casos de uso, la lógica de negocio y la persistencia. No se implementó una arquitectura de microservicios ni un framework de inyección adicional.

Inyección de dependencias: Depends() construye servicios y repositorios y permite inyectar los pesos. Hay un driver por proceso; no se comparte una sesión entre solicitudes. El lifespan verifica conexión, crea constraints y cierra el driver al apagar.

Normalización de datos

" Python " y "python" comparten la clave python. Se aplica trim y minúsculas a skills, ubicaciones y compañías. El primer nombre insertado, sin espacios en los extremos, queda como nombre visible del nodo compartido.

Las listas se deduplican; una habilidad que sea obligatoria y deseable se conserva únicamente como obligatoria. No se resuelven sinónimos, acentos ni espacios interiores: Bogotá y Bogota son claves diferentes. Los IDs externos conservan sus mayúsculas.

05 / Funcionamiento

Funcionamiento de la solución

Recorrido de una recomendación

Registro y actualización de entidades

1
Validar el contrato

Pydantic revisa campos, longitudes, números finitos, enums y listas; normaliza los valores admitidos.

2
Abrir una transacción de escritura

El repositorio ejecuta session.execute_write. MERGE identifica el nodo por su ID.

3
Reemplazar datos y conexiones

Actualiza propiedades, borra relaciones anteriores y reconstruye skills, ubicación, modalidad y compañía cuando corresponda.

4
Confirmar o revertir todo

Si algo falla, hay rollback. Si termina correctamente: 201 cuando se crea, 200 cuando se actualiza.

Generación de recomendaciones

1
Verificar la entidad base

La ausencia del candidato o de la vacante produce 404, no una lista vacía.

2
Prefiltrar mediante el grafo

Neo4j obtiene entidades distintas con al menos una habilidad compartida, obligatoria o deseable.

3
Puntuar cada pareja en Python

El motor calcula cuatro componentes y las explicaciones. Cypher no calcula el score.

4
Filtrar, ordenar y limitar

Aplica minScore al valor publicado, ordena por score descendente e ID ascendente, calcula total y aplica limit.

Upsert significa reemplazo completo. No es un PATCH. Omitir expectedSalary o description elimina su valor anterior; omitir desiredSkills equivale a una lista vacía. Las actualizaciones concurrentes se serializan en el nodo y la detección 201/200 se realiza dentro de la transacción.
06 / Algoritmo

Algoritmo de compatibilidad

Skills · 50%Exp. · 25%Lugar · 15%Modo · 10%
score(candidate, job, weights) → MatchResult

matchScore = round(
    skills * 0.50 + experience * 0.25
    + location * 0.15 + workMode * 0.10,
    1
)

01 · Habilidades

Con obligatorias y deseables: 70 × cobertura obligatoria + 30 × cobertura deseable. Cada cobertura es la proporción de habilidades presentes.

Sin deseables: 100% de cobertura obligatoria. Sin obligatorias: 100 puntos, aunque haya deseables.

02 · Experiencia

min(1, años / años requeridos) × 100. Si se requieren cero años, el componente es 100.

La experiencia adicional no aumenta el componente por encima de 100.

03 · Ubicación

100 puntos cuando las claves normalizadas coinciden o la vacante es remota. En otro caso, cero.

No se calculan distancias, zonas horarias ni permisos de trabajo.

04 · Modalidad

100 si coincide o alguna parte es any; 50 si son diferentes y una es hybrid; cero en los demás casos.

La API admite any solo para la preferencia del candidato.

Ejemplo: todas las skills, 1,5 años frente a 3 requeridos, misma ubicación y modalidad compatible → 50 + 12,5 + 15 + 10 = 87,5. El salario esperado se almacena, pero no puntúa.

Prefiltrado y cálculo de compatibilidad

Un score teórico alto no garantiza aparecer en el ranking: primero debe existir una skill compartida. Una vacante sin skills o un candidato con lista vacía no generan recomendaciones. matchingSkills incluye obligatorias y deseables presentes; missingSkills solo muestra obligatorias faltantes.

Los componentes se calculan sin redondear; el total se redondea a un decimal con Python. Los pesos son finitos, están entre 0 y 1 y deben sumar 1.

    08 / API REST

    Diseño e integración de la API REST

    Base de desarrollo: http://localhost:8000. Los datos usan camelCase. El prefijo /api/v1 versiona el contrato de negocio.

    GET
    /api/v1/jobs

    Catálogo de ofertas: q busca título, descripción o empresa; location filtra ciudad; workMode admite remote, hybrid u onsite; limit (1–50) y offset (≥0) paginan. Devuelve total, limit, offset e items, ordenados por ID.

    GET
    /api/v1/candidates/{id}/jobs/{job_id}/diagnosis

    Compara cualquier candidato y vacante existentes. Devuelve habilidades obligatorias faltantes, coincidencias, score, desglose y passesSkillPrefilter, incluso cuando no comparten habilidades. Responde 404 si alguna entidad no existe.

    POST
    /api/v1/candidates

    Crear o reemplazar un candidato por ID externo. 201 / 200.

    GET
    /api/v1/candidates/{id}

    Consultar un candidato. 200 / 404.

    POST
    /api/v1/jobs

    Crear o reemplazar una vacante. 201 / 200.

    GET
    /api/v1/jobs/{id}

    Consultar una vacante. 200 / 404.

    GET
    /api/v1/candidates/{id}/recommendations

    Vacantes para un candidato; admite limit y minScore.

    GET
    /api/v1/jobs/{id}/candidates

    Candidatos para una vacante; admite limit y minScore.

    GET
    /health

    Comprueba que el proceso API responde.

    GET
    /health/db

    Verifica conectividad real con Neo4j.

    Extensibilidad del algoritmo

    1. Para cambiar pesos, ajusta Weights o la dependencia get_weights().
    2. Para sustituir la lógica, inyecta un callable scorer en MatchingService con la firma (Candidate, Job, Weights) → MatchResult.
    3. Conserva los contratos públicos y verifica los nuevos casos con tests unitarios, luego con la integración.

    Un ejemplo válido de pesos alternativos es Weights(skills=0.60, experience=0.20, location=0.10, work_mode=0.10). Es una posibilidad de extensión; el MVP utiliza 0.50 / 0.25 / 0.15 / 0.10.

    11 / Evaluación y evolución

    Decisiones de diseño y mejoras futuras

    DecisiónBeneficioCoste o límite
    Reglas y pesos, sin MLResultado explicable y verificable con pocos datos.Los pesos no se aprenden; requieren criterio del negocio.
    Grafo como prefiltroConecta entidades por relaciones explícitas.Excluye parejas sin skills comunes incluso con compatibilidad por otros criterios.
    Scoring en PythonAlgoritmo puro, sustituible y fácil de probar.Todos los pares prefiltrados se puntúan en memoria.
    Transacciones de reemplazoEstado final consistente y actualizaciones repetibles.Los catálogos huérfanos pueden acumularse.
    Servicio síncronoFlujo simple y driver oficial sin infraestructura extra.Los handlers usan el pool de hilos; la capacidad debe medirse.
    API Key mínimaPunto de extensión sencillo.No provee autorización por propietario ni multitenancy.

    Limitaciones actuales

    • No se han ejecutado pruebas de carga; el coste del ranking crece con las parejas prefiltradas.
    • No hay limpieza automática de catálogos huérfanos de producción.
    • La lectura de la entidad base y el prefiltro no comparten una instantánea única frente a escrituras concurrentes.
    • El catálogo de ofertas admite offset; el ranking solo admite límite y umbral. No hay perfiles de usuario autenticados ni control de acceso por entidad.
    • No se normalizan sinónimos ni equivalencias geográficas.
    Fuera del alcance implementado: Redis, PostgreSQL, colas, ML, notificaciones y CI/CD. Las posibles mejoras anteriores no están implementadas ni son requisitos para ejecutar el MVP local.
    Glosario breve

    API REST: interfaz HTTP para intercambiar recursos. Schema: contrato de datos y validación. Upsert: crear si no existe o actualizar si existe. Constraint: regla de integridad en la base. Transacción: conjunto de operaciones que se confirma o revierte completo. Cypher: lenguaje de consultas de Neo4j. Dataclass: modelo de datos Python. ASGI: interfaz entre la aplicación web y el servidor. Bolt: protocolo de conexión del driver Neo4j.

    Demostración: una oferta que no aparece en el ranking

    Un candidato sin habilidades compartidas queda fuera de recomendaciones. El endpoint de diagnóstico directo sí responde y muestra las habilidades obligatorias faltantes. Esto permite explicar cómo mejorar el perfil sin confundir la puntuación teórica con el prefiltro del grafo.

    Puertos de esta verificación: API en 18000 y Neo4j Browser en 17474, para coexistir con el prototipo anterior. En una instalación nueva, Compose usa 8000, 7474 y 7687 por defecto. Puedes configurarlos con API_PORT, NEO4J_HTTP_PORT y NEO4J_BOLT_PORT en .env; para Python local, ajusta también NEO4J_URI si cambias Bolt.
